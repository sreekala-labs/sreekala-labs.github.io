---
title: "The N+1 Query, and Why It Hides in ORMs"
topic: SQL
summary: "One query to fetch the list, N more because you looped over it."
---

The pattern is always the same shape: fetch a list of N records, then loop
over the list and fetch a related record for each one. One query becomes
N+1 queries, and it's invisible in the code because the ORM is doing the
looping for you.

```python
orders = Order.objects.all()        # 1 query
for order in orders:
    print(order.customer.name)      # +1 query per order
```

## Why it's easy to miss

The code reads like a single logical operation. Nothing in the syntax
signals that `order.customer` is a network round trip, so it looks free.
It shows up in profiling as "the database is slow" when the real issue is
"the database is being asked 500 times instead of twice."

## The fix

Tell the ORM to fetch the relationship up front, in the same query or one
additional batched query:

```python
orders = Order.objects.select_related('customer')   # 1 JOIN query
# or, for many-to-many / reverse FK:
orders = Order.objects.prefetch_related('items')     # 2 queries total
```

`select_related` does a SQL JOIN and pulls everything in one round trip —
good for one-to-one and foreign-key relationships. `prefetch_related` runs
a second query and stitches the results together in Python — better when
the join would multiply rows (one-to-many, many-to-many).

## The direction that matters in an interview

Given a slow endpoint and a suspicious query count in the logs, the
diagnostic question isn't "what's the query plan" first — it's "where is
this being called inside a loop." The fix is almost always eager loading
the relationship before the loop starts, not optimizing the query itself.
